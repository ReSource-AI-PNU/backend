# D 트랙 코드·로컬 동작 검토

검토일: 2026-11-16 (한국 시간)

## 판정

기본 시연 흐름은 작동하지만, 현재 코드를 완료로 판정할 수 없다. 기존 자동 검사는 통과했으나 추가 재현에서 우선 수정해야 할 결함 4개를 확인했다. 아래 통과 표시는 검사한 범위에 한정하며, 결함이 전혀 없다는 보장은 아니다.

이번 작업에서는 구현 코드와 기존 테스트 파일을 수정하지 않았다. 별도 임시 SQLite DB에서 기존 테스트 도우미와 HTTP TestClient를 사용했다. 기존 사용자 진단 DB는 변경하지 않았다.

## 실제 재현한 결함

### 1. P1 — 비공개 기업 물량이 응답에서 역산됨

- 위치: `app/platform/service.py:105`, `app/platform/service.py:342`, `app/platform/service.py:89`.
- 재현: 300kg 배출 기업이 묶음 참여 동의 완료 후 자기 진단을 조회한다. 다른 기업의 `group[].kg`는 null이다.
- 실제 결과: 총량 1,230kg와 다른 기업의 `costShare[].sharePct`가 그대로 반환된다. 이를 곱하면 각각 420kg, 510kg가 정확히 복원된다. 다른 기업 하나만 방문하는 차량의 `trips[].kg=510`도 그대로 노출된다.
- 영향: 화면에 비공개라고 표시해도 API와 상세 순회 정보로 개별 물량을 알 수 있다.
- 수정 방향: 조회자별 응답 정책을 비용 분담률·차량 총량 등 파생 필드에도 적용하고, 외부 서비스 전달용 원본과 화면용 응답을 분리한다.
- 완료 기준: 타사 물량 null 여부뿐 아니라 응답의 파생 값으로 개별 물량이 복원되지 않는지 검증한다. 어떤 합계 정보를 공개할지도 명시해야 한다.

### 2. P1 — 협상 승인 후 기존 매칭·비용·이행안이 남음

- 위치: `app/platform/api.py:473`의 협상 승인 처리.
- 재현: 이행안까지 계산 → 월 2회 협상 → 합의안 승인.
- 실제 결과: `bundles[0].schedule`은 목요일 오전·월 2회로 바뀌지만, `session.matching.bundles[0].schedule`은 미확정 상태다. 기존 매칭·비용·이행안 객체가 모두 그대로 유지된다. 그 기존 이행안에 대한 최종 승인도 HTTP 200으로 성공한다.
- 영향: 후속 서비스가 받는 매칭 스냅샷과 화면의 수거 조건이 다르고, 변경 전 조건으로 만든 문서를 승인할 수 있다.
- 수정 방향: 협상 승인 시 매칭 결과를 갱신하고 비용·이행안을 무효화하며 상태를 재계산 단계로 되돌린다. 후속 서비스 입력에 승인 단가·요일·시간·횟수가 반영되는지도 확인한다.
- 완료 기준: 조건 변경 직후 예전 이행안은 승인되지 않아야 하고, 재계산한 결과에 변경 조건이 전달되어야 한다.

### 3. P1 — 매칭 뒤 생성된 확인 질문에 답할 수 없음

- 위치: `app/platform/api.py:290`.
- 재현: 참여 동의를 마친 진단에서 비용 서비스가 계약에 맞는 숫자형 질문을 반환하도록 로컬 어댑터를 대체한다. 외부 네트워크 호출은 하지 않는다.
- 실제 결과: 진행은 `cost-carbon` 단계에서 질문 답변을 기다리지만, 질문 답변 API는 묶음이 있다는 이유로 HTTP 409를 반환한다.
- 영향: 비용·이행안 단계의 정상적인 추가 질문이 나오면 해당 진단을 끝낼 수 없다. 새 진단에서도 같은 질문이 나오면 다시 막힌다.
- 수정 방향: 기존 조건을 변경하는 상류 단계 질문과 새로 발생한 후속 단계 질문을 구분한다. 답변에 영향받는 결과만 초기화한다.
- 완료 기준: 매칭 후 비용·이행안 질문을 저장하고 재실행할 수 있어야 하며, 확정된 기존 조건을 바꾸는 답변은 별도 정책으로 통제해야 한다.

### 4. P1 — 여러 흐름 중 하나만 매칭해도 전체 승인 가능

- 위치: `app/platform/orchestrator.py:40`, `app/platform/api.py:379`, `app/platform/delivery.py:28`.
- 재현: 확인된 LDPE/PCR 흐름 2개 등록 → 첫 흐름만 수동 묶음 계산·참여 동의 → 이행안까지 실행 → 최종 승인.
- 실제 결과: 경로 판정은 두 흐름 모두 bundle이지만 묶음은 하나만 존재한다. `blockedStep=null`, 상태는 `awaiting-approval`이고 최종 승인 HTTP 200이다.
- 원인: 첫 묶음의 회신이 `session.matching`을 채운다. 실행기는 결과 객체가 있다는 이유로 나머지 흐름의 매칭을 건너뛴다. 최종 승인도 존재하는 묶음의 준비 여부만 확인한다.
- 영향: 매칭·참여 동의를 받지 않은 흐름까지 완료된 것으로 처리된다.
- 수정 방향: 외부 거래가 필요한 전체 흐름 ID와 매칭 결과의 흐름 ID를 대조한다. 실행 단계와 최종 승인 양쪽에서 누락을 차단한다.
- 완료 기준: 두 번째 흐름의 거래처·묶음 조건을 충족하기 전에는 최종 단계 진행 및 승인이 차단되어야 한다.

## 화면에서 확인한 보완점

- 이웃·업체 수신함은 `sessionId`를 받지만 진단 이름·번호를 표시하지 않는다. 같은 업체와 재질의 제안이 여러 건이면 사용자가 어느 진단인지 구분하기 어렵다. `frontend/src/components/platform/workbench.tsx:880`.
- 참여 상태 `self`를 조회자와 관계없이 '우리 회사'라고 표시한다. 이웃 기업으로 보면 다른 참여 기업에 '우리 회사'가 붙는다. 현재 조회 기업 ID를 기준으로 표시해야 한다. `frontend/src/components/platform/workbench.tsx:100`.
- 담당자 권한에서도 승인 버튼을 누를 수 있고 나중에 서버가 403으로 막는다. 권한 차단은 작동하지만 버튼 설명·비활성화가 필요하다. 에러가 페이지 상단에만 표시되어 사용자가 결과를 놓치기 쉽다.
